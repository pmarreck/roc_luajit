- [x] (09:40 EDT 2026-10-02; dict_ops wall -47..-52%, RSS -70..-73%) Perf (dict_ops GC): record tables stored in lists (per-element `{k, v}`). The owner 08:12 EDT 2026-10-02: "Let the decisions be guided by measurements of performance and memory usage. Lean more towards performance." Prototype, measure, keep only on a win. Measured 22:00 EDT: 158,814 `R.m38` pair tables per 20,000 inserts (Dict's bucket-shifting loop ll_get + ll_set, and entry appends), ~70% of dict_ops' remaining allocation; GC is 15% of its instructions. Design sketch for "flat storage":
  - An element layout whose flattened shape has k >= 2 leaves is stored inline: element i of a list with offset o occupies allocation slots (o+i)*k+1 .. (o+i)*k+k. Single-leaf elements (numbers, Str, List, Box) keep k = 1, so their code paths and costs do not change.
  - list.lua takes k beside w; capacity, length and offsets stay in elements. get returns k values; set/append/prepend take k values; copy/concat/sublist/drop/swap/reverse move k slots per element. The emitter passes k from the element shape and assigns leaves directly (no `rS` + `R.uN`, no `R.mN`).
  - Element RC helpers get a leaf form (`R.dN` over k values). ll_sort_with materializes the two elements for each comparator call, or sorts an index permutation, whichever measures faster.
  - Boundaries that need whole elements (hosts' record lists: HTTP headers, SQLite bindings, directory entries; static list data; list_replace's record result) convert explicitly with the existing materializers.
  - Tests: every suite plus alloc_budget (dict_ops expected well under 300 bytes/op) and an emitted_layout check that no `R.mN` call appears in a list element position for k >= 2. Candidates: one-field structs represented as their field (native layout is identical); flat element storage for record lists. Measure the share first.
